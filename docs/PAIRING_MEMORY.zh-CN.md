# ESP32-C3 配对内存修复

当 iPhone 发送较大的加密配对资料时，BLE 接收缓冲、密文 JSON、解密明文、凭据副本和配置任务栈可能同时占用内部堆。即使总空闲堆看似充足，AES DMA 或任务栈需要的连续内存仍可能申请失败，设备随后返回等待配对。

## 应用源码调整

- BLE 分片按首片长度和片数估算容量，必要时增长，继续保留 8192 字节消息上限和分片顺序校验。
- Base64url 直接解码到调用方缓冲，完整验证输入后才写入，不创建补齐密文的临时副本。
- 解密成功后先释放外层 JSON；复制完凭据后清零并释放内层 JSON。等 GATT 回调释放明文、重组缓冲和扁平化数据包后，再创建配置任务。
- 配置任务使用 4096 字节栈；本适配层的回调保存配置，TLS 由单独的工作线程处理。若修改回调以同步执行其他业务，需要重新测量栈余量。
- 配对期间不分配聊天解析器，在 BLE 关闭后建立云连接时再初始化；未初始化或已停止时，聊天 API 安全返回。

失败、取消、会话变更和任务创建失败时，独立拥有的凭据均由同一清理函数清零后释放。加密认证、实体确认和禁止明文配对的要求保持原有流程。

## ESP-IDF 5.5.3 的 AES DMA 配套补丁

本仓库未收录 ESP-IDF 源码。[补丁](../patches/esp-idf-v5.5.3-aes-dma-chunk.patch) 仅修改 [Espressif v5.5.3 官方 AES DMA 实现](https://github.com/espressif/esp-idf/blob/v5.5.3/components/mbedtls/port/aes/dma/esp_aes_dma_core.c) 的非 ESP32-P4 分支，将 `AES_MAX_CHUNK_WRITE_SIZE` 从 1600 调整为 512。原有分块循环、DMA 内存属性、GCM 认证和计数器处理不变；512 是 AES 块长 16 的整数倍。

补丁修改整个 SDK 的对应分支，会影响使用同一 SDK 的其他 AES 调用；较小分块可能增加吞吐开销。应在自己的 SDK 工作副本中审查，不要直接覆盖共享 SDK 或对不同 IDF 版本强行套用。P4 的 8 KiB 分支不变。

在 ESP-IDF 5.5.3 根目录执行（将补丁路径替换成实际路径）：

```bash
git apply --check /path/to/ai-passport-muse/patches/esp-idf-v5.5.3-aes-dma-chunk.patch
git apply /path/to/ai-passport-muse/patches/esp-idf-v5.5.3-aes-dma-chunk.patch
```

应用源码改动不会自动应用 SDK 补丁。完整宿主工程还需重新集成、编译并在目标设备验证。更换 SDK 版本时需重新核对该实现。

## 验证范围

`bash tools/test-host.sh` 包含真实 RX/命令分发代码和 Base64url 解码器的 ASan/UBSan 回归：消息边界、非等长分片、逐个内存申请失败后重试、任务创建失败、取消/关闭、过期会话、凭据清零，以及加密配对和实体确认门槛。测试在创建配置任务的边界检查：存活分配只能属于独立复制的配置参数。Base64url 使用随机固定种子向量、容量边界及全部非法字节验证，编译时禁止该解码器分配堆。

BLE、FreeRTOS 和解密入口由 host 测试替身提供；这里不验证无线时序、真实 AES/GCM、SDK 补丁运行效果或实际栈余量。聊天测试另覆盖解析器启动前、停止后和再次启动的调用。

此前在一台 ESP32-C3 上，采用相同内存调整思路的本地二进制补丁完成过 iPhone 配对并进入云端 ready，配置任务 4 KiB 栈最小剩余约 1.7 KiB，观察窗口内未见内存申请失败。这只是该设备的有限验证，不等同于本 PR 源码已重新构建或完整验收。

本次源码提交未构建、打包或刷写整机固件。本仓库缺少完整宿主工程；维护者仍需验证新编译固件的首次配对、取消重试、退出重进、云连接、语音回复、AES 兼容性及长时间运行。原始日志、备份、固件镜像、账号资料和实际网络配置均不公开。
