# 让 Agent 配好 Muse

面向 Codex、Claude Code、WorkBuddy 等能访问用户电脑文件与终端的 Agent。纯网页聊天或远端任务只能指导；系统界面操作取决于 Agent 的实际工具。普通使用不用编译，不需要安装随身语音客户端、虚拟声卡或输入法。

## 1. 给用户的复制指令

用 Agent 打开解压后的完整项目目录，复制：

```text
请帮我配置本项目的 AI Passport Muse，直到设备收到真实文字回复。
先阅读 AGENTS.md、docs/AGENT_SETUP.zh-CN.md、QUICKSTART 和 NETWORK。
检查设备是否已经有 Muse，已有则跳过刷机。识别我的电脑系统和网络，
优先使用设备可直连的网络；需要代理时检查我已有软件的 HTTP/混合端口、
真实局域网 IPv4 和监听情况，不使用作者地址或猜测端口。
能自动检查和配置的部分直接完成；变更代理局域网监听和防火墙前，
说明具体范围并取得我对这项操作的确认，不关闭整个防火墙。
账号由我登录，Token 由我在本地设备设置页填写，不让我贴到聊天或日志。
引导我完成 Wi-Fi、手机 Muse 配对和硬件按键确认，等待“我准备好了”，
再让我亲自说话，验证手机收到语音、硬件出现回复，接着做第二次与重进测试。
不自动录音发送，不为普通网络失败清除配对，也不猜设备配置 API。
用本地 .setup/progress.json 记录不含凭据的进度，中断后复检并继续。
最后分别报告电脑检查、设备联网、配对、云端就绪和实际回复的结果。
```

没有项目时，将仓库地址 `https://github.com/manchunx7-bit/ai-passport-muse` 交给 Agent，先获取完整项目再执行。设备固件从 README 指定官网入口获取，不把 Source code ZIP 当成固件。

## 2. 先确定要做哪些步骤

| 用户现状 | 处理 |
| --- | --- |
| 设备能打开 Muse | 保留现有系统，直接检查配置与网络 |
| 设备没有 Muse | 阅读 [固件说明](FIRMWARE.zh-CN.md)，核对官网型号/版本与备份流程；不自行编译整机 |
| Muse 已能正常回复 | 记录启动方式，无需重填 Token 或重新配对 |
| 没有自己的账号/SDK Token | 引导至 [官方申请页](https://gadgets.muse.ai/)，用户登录申请；账号权限问题不能靠刷机解决 |
| 设备可直连 | 代理留空，不安装电脑代理服务 |
| 设备无法直连，已有电脑代理 | 按下一节检查 HTTP/Mixed 端口和局域网可达性 |

账号申请、依赖下载、说明文档应在连接设备热点**之前**准备好。热点不提供互联网；优先让手机连接热点，电脑留在正常网络。确实要让电脑切换热点时，先保存进度和离线教程，避免 Agent 会话断网后丢失步骤。

## 3. 自动检查电脑端，再处理设备端

新增的只读诊断只需 Python 3.9+ 标准库，没有 Python 时使用 [网络教程](NETWORK.zh-CN.md) 的原生命令，不为填两个字段强制安装开发环境。以下命令从项目根目录运行：

```bash
python tools/setup_doctor.py --json
```

先在现有代理软件界面确认 HTTP 或 Mixed 端口。假设用户实际查到端口为 7900，再运行（示例数字需替换）：

```bash
python tools/setup_doctor.py --proxy-port 7900 --json
```

上面的 `python` 是 Windows 常见启动名；Mac 使用 `python3`，Windows 安装了启动器也可使用 `py -3`。Agent 可复用本机已有的 Python 3.9+，不假定系统一定有 `python` 命令。

工具读取默认路由下的局域网 IPv4 候选和指定端口的监听信息；不扫描端口、不读取订阅或 Token、不发联网请求、不修改防火墙。存在多个候选时，Agent 必须结合当前路由器和物理网卡确认。VPN/TUN 或访客隔离可能影响结果，不把候选地址直接当成设备可达证明。

| 检查 | 通过后仍要做什么 |
| --- | --- |
| `lan_ipv4` 有候选 | 核对电脑与设备在同一可互通局域网 |
| `proxy_listener` 监听所有 IPv4 或候选 LAN 地址 | 确认这是 HTTP/Mixed 代理，不是 SOCKS/API 端口 |
| 只监听 127.0.0.1 | 在代理软件开启 Allow LAN，必要时确认局域网范围的防火墙规则，再复检 |
| 未找到/无权限读取监听 | 按错误检查进程、实际端口、权限；不能记为端口正常 |

诊断返回 `LOCAL_CHECKS_PASSED` 只表示所选电脑检查通过；不代表设备可达、HTTP 代理可用或 Muse 登录成功。未指定代理端口时代理检查为 `NOT_RUN`，不表示需要安装代理。

结构化报告 `schema_version` 为 1，每项检查包含 `id/status/detail/next_action`，并列出 `pending_user_actions`。退出码 0 表示所选本地检查通过，1 表示有缺项/失败，2 表示命令参数错误。`cloud_connection`、`device_configuration`、`real_reply` 始终为 `NOT_RUN`，由后续设备操作单独验收，不被电脑自测覆盖。

需要验证出口时，按网络教程通过用户自己的代理运行 curl，保持 TLS 验证。分清 TCP 端口、代理 CONNECT/TLS、账号认证、设备会话和真实回复：根路径 404/405 只说明传输层到达目标；407 是代理认证问题；502/503 或 DNS 错误不能算云端可用。电脑成功仍需设备实测。

## 4. 用户填写与配对：每次只推进一步

1. 用户让设备退出 Muse，打开手机设置；手机连接屏幕所示热点，浏览器打开屏幕地址。没有互联网提示时保持热点连接。
2. 用户选自己的 2.4 GHz Wi-Fi 并填密码；在“个人资料 → Muse 语音助手”填自己的 Token。账号、Token 和密码不经过聊天。
3. 直连时代理两项留空；需要代理时 IP 和端口分开填。IP 不带 `http://` 或端口；使用刚核对的实际值。
4. 点击“保存 Muse 配置”，确认成功，再完成设置。Token 不回显是正常行为，空白保留已有 Token；只修改代理保留配对，更换 Token 会清除旧配对。
5. 手机退出热点恢复联网；设备连接路由器。打开设备 Muse，按 [完整教程](QUICKSTART.zh-CN.md) 在手机 Muse 开发者模式添加对应尾号设备；由用户在硬件短按确定。
6. 手机出现设备条目后，还要等硬件“我准备好了”；未就绪先查网络与错误提示，不先清除配对。

页面/手机 App 的入口可能随版本变化，以当前官方界面为准。无法观察界面时，让用户报告这一项的成功提示，不连续堆积一长串未确认操作。

### 为什么暂时不直接调用设备 API

本仓库公开的是 Muse 模块，整机设置服务器和会话认证不在仓库中。目前没有在本项目公开并验收的跨固件自动配置 API 契约。Agent 应使用设备官方设置页，不能猜 URL、跳过认证或声称已经写入配置。

将来接入配置助手前，维护者需提供：支持的固件版本、进入/退出设置模式的方法、会话鉴权、读取“已配置/已配对”的脱敏响应、写入字段与留空语义、失败响应和设备退出应用要求。接口必须经过相应版本实测；不能以当前私有源码推断用户旧版固件支持。

## 5. 真实验收与结果

由用户在屏幕亮起且显示“我准备好了”时按住上键，说无敏感信息的测试句后松开。核对手机收到语音，等待硬件显示相关最终文字。等待期间不按下键取消、不启动下一段录音。然后再做一次，最后长按确定退出再进入，检查是否可保留授权继续使用。

| 阶段 | 成功证据 | 失败时优先检查 |
| --- | --- | --- |
| 设备联网 | 设备已连接所选路由器 | 2.4 GHz、密码、访客隔离 |
| Token 保存 | 设置页保存成功，或明确显示已配置 | 页面提示；不要求读取原 Token |
| 手机配对 | 对应尾号设备添加完成、硬件确认过 | App 开发者模式、手机权限 |
| 云端就绪 | 硬件“我准备好了” | DNS、代理出口、明确的认证错误 |
| 首次/第二次请求 | 手机收到语音、硬件收到最终回复 | 发送/等待阶段，勿只凭“思考中”算成功 |
| 重进 | 保留授权并恢复就绪 | 电脑代理运行、IP/端口变化 |

Muse 当前是语音输入、文字输出，没有 TTS；单次最长 30 秒，硬件仅保留最新回复前 1023 个 UTF-8 字节。不要把没有声音当故障，也不要把 host 编译或网络检查当成对话验收。

## 6. 记录进度与以后继续

Agent 将不含凭据的进度保存到 `.setup/progress.json`，不是设备配置，不存在 `setup --resume` 命令：

```json
{
  "schema_version": 1,
  "application": "muse",
  "updated_at": "实际检查时间（ISO 8601）",
  "network_mode": "direct",
  "steps": {
    "device_wifi": {"status": "USER_ACTION", "evidence": "待设备确认"},
    "pairing": {"status": "NOT_RUN", "evidence": "尚未配对"},
    "reply": {"status": "NOT_RUN", "evidence": "尚未发送语音"}
  },
  "next_action": "用户在设备设置页填写 Wi-Fi 和 Token"
}
```

状态为 `PASS`、`FAIL`、`USER_ACTION`、`NOT_RUN`。不存 Token、密码、配对材料、订阅、录音或对话原文。诊断报告含本机地址与进程信息，只保留本地，分享前脱敏。

重启/换网后，用户可说：“继续配置 Muse，读取 .setup/progress.json，重新检查当前网络和代理，保留 Token 与配对，继续未完成的实际回复测试。”重查 IP、监听和设备就绪，不能永久复用旧的通过状态。

最终报告分别列出自动检查、用户确认、实际回复、待验证项目及下一步。直连成功后只需打开设备 Muse；借用电脑代理时说明电脑需保持开机、代理运行、局域网地址可达。仅有电脑检查结果时明确写“电脑端检查完成，设备与对话待验证”。
